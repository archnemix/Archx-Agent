# Workarounds

## GitHub Actions for constrained environments

When local resources or network access are insufficient, use a deliberately triggered workflow with scoped paths. Store required logs and outputs in organized repository directories, not only as Actions artifacts; avoid recursive triggers when committing results. Cap concurrent runners at five. For tests, use Linux, Windows, and macOS runners, recording commands, inputs, and outputs by version, retaining only the current and two previous versions. Never write credentials into the repository or logs. Create the workflow only when a concrete job requires it; document its trigger and output locations here at that time.

## Native GUI builds without a local Rust toolchain

The current sandbox has no `rustc` or `cargo`. `.github/workflows/gui.yml` deliberately triggers on source/config changes or edits to `internels/ci-trigger.txt`. It runs Linux, Windows, and macOS sequentially (no more than one runner concurrently), commits build/test logs and running-app screenshots to `Docs/Test_Results/Unreleased/`, and places the Windows portable executable at `deliverables/Unreleased/windows/archx-ai-lab.exe`. Generated-result commits do not match the workflow's trigger paths. The user chose repository-hosted binaries; monitor repository size and retain only the current plus two previous versions. The first successful build and screenshots are recorded in `Docs/Test_Results/Unreleased/Gui_Validation.md`. The macOS runner's available desktop size limited its capture to 1024 × 642, whereas Windows/Linux captured 1280 × 800; record actual dimensions rather than claiming identical pixels. The user should review the Windows build before Step 2. Snapshot mode is opt-in via `ARCHX_SNAPSHOT=<path>`.

## Actual 3D artwork work is not covered by static screenshot CI

The current `gui.yml` captures Home/About plus synthetic frozen text-hover phases per OS; those prove distinct visual states but cannot prove physical mouse movement or a future 360-degree Agent animation. The current user direction reserves genuine animated 3D imagery for **Archx Agent only**; Training and Fine-tuning now use inexpensive text hover. A genuine Agent solution needs an approved 3D mesh or authoring pipeline, a 3D renderer or pre-rendered multiview frames, timed hover state in the Iced app, and deterministic start/mid/end captures per OS. Do not use a flat 2D image spin as a substitute. An attempted local `bpy` 4.5.16 import failed with `ImportError: libXrender.so.1`; this sandbox's Debian package mirror is unreachable, so local Blender rendering cannot be validated here. Prefer a dedicated CI authoring/render pipeline or a suitably licensed model source if proceeding without locally available graphics libraries. Keep generated assets bounded and reproducible.

## Windows verified-publisher prerequisite

The current unsigned portable exe has a PE certificate directory offset and size of zero. The Windows VersionInfo `CompanyName=Archnemix` and file icon are descriptive, not a trusted signature. Obtain an appropriate publicly trusted code-signing certificate/service issued to the verified Archnemix legal entity (the displayed publisher follows the certificate subject), using a provider that supports the entity's actual jurisdiction. Microsoft's public-trust Artifact Signing quickstart lists restricted organization/individual eligibility by location; do not assume that service is available to the entity. Follow the chosen issuer's security/storage instructions, sign only the release artifact in a locked-down pipeline after build and verification, timestamp it, and verify its Authenticode signature with Microsoft SignTool or `Get-AuthenticodeSignature` before delivery. Do not request private keys or passwords in chat; GitHub secret names should be documented only after a method and owner are agreed. Signing cannot be completed by changing metadata or creating a self-signed certificate.
