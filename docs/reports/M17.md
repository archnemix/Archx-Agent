# M17 completion report - Memory persistence foundation

## 1. Objective

Persist six distinct memory systems (active, permanent, archival, project, solution,
learning) with documented scope, provenance, lifetime, rejection rules and retrieval
behaviour - used consistently by the app, and surviving restart and crash.

## 2. What was built

* `managers/memory.py` (~1,600 lines): one `memories` table with a `kind` discriminator
  plus per-kind validation, history snapshots, sources, retrieval log, artifacts on disk,
  retention.
* Schema v3: `memories`, `memory_history`, `memory_sources`, `memory_retrievals`,
  `learning_events`; v2 `projects` for project identity.
* `managers/projects.py`: project identity, slug uniqueness, archive (never a silent
  delete of project memory).
* `managers/conversation.py`: conversations and messages with sequence ordering.
* CLI: `memory add|list|show|history|search|edit|delete|retrieve|profile|policy|stats|retention`
  and `projects create|list|show|rename|archive|link`.
* Write kinds: `memory.add`, `memory.update`, `memory.status`, `memory.delete`,
  `memory.source`, `project.create`, `project.update`, `project.delete`.

## 4. Decisions that shaped it

* **One table, six policies.** Governance (provenance, history, sources, artifacts) is
  identical for all six kinds; only the rules differ. Six tables would have duplicated
  the governance five times over.
* **Unverified solutions are stored but not injected.** The corpus is only useful if
  "verified" means something; `verification` is required and a verified solution needs
  evidence text.
* **Soft delete is the default.** `memory delete` hides a memory; the row and its history
  stay, `--hard` requires an explicit flag, and a tombstone (checksum only) records the
  removal.
* **Artifacts on disk, metadata in SQLite.** Large blobs bloat every backup; the file
  path is stored inside the artifacts root with a containment check and a checksum that
  is verified on read (a tampered file is refused, not silently returned).
* **Credentials are refused, not redacted, in memory.** Storing `[REDACTED]` where a
  password was looks like a fact and is worse than an error; `memory add` fails and tells
  the user to use the credential store. `secret://` *references* are accepted because
  they contain no secret.

## 5. Limitations (recorded, not hidden)

* No GUI yet (M29), so memory management is CLI-only.
* `memory retrieve` is a preview of the same code path the chat uses; the chat surface
  arrives with M16/M19 wiring and is exercised in `tests/test_application.py`.
* Project memory isolation is enforced by scope id, not by filesystem sandboxing; the
  project path is only validated for containment.
* Embedding state is `awaiting` until M18 backfill - retrieval says so instead of
  pretending semantic search happened.

## 6. What this unlocks

M18 (embeddings) can now attach vectors to stable, versioned memory ids; M19 can spend a
token budget over them; M22 (permissions) can reuse the same write-coordinator and trace
paths; M24 (task history) can reference memory ids instead of duplicating content.
