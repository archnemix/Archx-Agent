# M19 completion report - Context Strategy Manager

## 1. Objective

Five user-selectable context strategies that build the window deterministically, explain
every inclusion and omission, count tokens honestly, never delete stored history, and never
silently drop the current request or pinned content.

## 2. What was built

`managers/context.py` plus schema v4 (`context_manifests`, `context_summaries`) and v11
(`context_proposals`):

| strategy | behaviour | guarantee |
|----------|-----------|-----------|
| `oldest_first` | keep the newest turns that fit, report the rest as omitted | stored history untouched |
| `summarize` | summarise the older range into a stored summary (with source range and generator) and keep recent turns verbatim | originals preserved; summary traceable to `[start_seq, end_seq]` |
| `ai_select` | score each message against the current request (token relevance, pinned, recency) and record the reason for every include/omit | every decision has a stated reason |
| `manual` | include exactly the messages the user picked (plus pinned) | anything not selected is reported, not lost |
| `ai_proposed` | persist a proposal (`context_proposals`), require explicit approval, then apply it and record `proposal_id` + `applied_manifest_id` | nothing changes before approval; rejection is recorded and blocks application |

Shared machinery: token budget (`context_limit - output_budget - reserve`, memory share
inside it), a per-message overhead term so manifests match what the model actually sees,
tool-call/result grouping as one unit, pinned protection, overflow errors that carry
numbers and an instruction, persisted manifests, and a trace event per build.

## 3. How it was verified

`tests/test_context_m19.py` - 24 tests: budget arithmetic; current request must fit
(`ContextOverflowError` naming the numbers); unknown strategy rejected; tokens never exceed
the budget; newest turn survives `oldest_first` and omissions are explained; pinned content
protected and an impossible pin raises instead of silently dropping;
tool call/result pairs kept together; manifest persisted and traced; memory counted in the
same window and injected as untrusted data; summary created with a source range while
originals stay; short conversations not summarised; summariser failure and absent
summariser reported as degraded; `ai_select` selects a relevant message with reasons;
`manual` includes only the selection (pinned included with its reason) and explains an
over-budget selection; proposals change nothing until approved; approval applies the
summary, records `approved_at`/`applied_manifest_id`, preserves history; rejection is
recorded and makes the proposal unapplicable.

Real run (`docs/VERIFICATION.md`): all five strategies produced manifests at a 120-150
token budget; every omission carried a reason (`older turn dropped...`,
`replaced in-context by summary ...`, `not selected (score 0.00, low relevance)`,
`not selected manually`); the stored message count was unchanged after
`summarize` and `ai_proposed`; summaries record `generator: simulated-test-double` when the
test double produced them, so a simulated summary can never be mistaken for a model
summary.

## 4. Decisions and what they cost

* **Explicit errors instead of silent truncation** for the current request and for pinned
  content. Cost: a user with too many pins gets a failure - with instructions - rather
  than a quietly degraded answer.
* **Per-message overhead counted.** Manifests initially under-reported (12 tokens per
  message of prompt scaffolding), which let a "within budget" build overflow. The
  overhead is now part of the arithmetic and the final trim removes the *oldest*
  droppable message, never the newest.
* **Summaries are stored with their source range and generator**, and `save_summary`
  supersedes an overlapping summary rather than accumulating duplicates. Cost: an extra
  write per summarisation.
* **Proposals are first-class rows**, not transient objects: rejection must be
  inspectable later and must block a stale approval, which a transient object cannot do.
* **`ai_select` is deterministic token scoring, not a model judgement**, and says so in
  the manifest notes. A model-based selector would cost a request per message and could
  not be verified without model weights here; the reason list is the same shape either way.

## 5. Limitations

* `ai_select`'s relevance signal is lexical (it can reuse embeddings through memory
  retrieval but does not embed individual messages). A message that is semantically but
  not lexically related can be omitted - and the manifest will say
  `score 0.00, low relevance`, so the omission is auditable rather than mysterious.
* `ai_proposed` builds its proposal from budget arithmetic, not from model reasoning. It
  is honest about that (`rationale` string), and the approval gate is the real safeguard.
* Summaries must be generated by a model; with no weights available the transcript shows
  the test double. A summary made by a real model is not demonstrated here.
* No automatic trimming of the *system* prompt beyond `extra_instructions` accounting;
  a huge user instruction still raises.

## 6. What this unlocks

M22 (tools) can reserve budget for tool schemas through the same manifest; M25 (agent
workflows) needs deterministic, auditable windows per step; M29 (GUI) can render
`included`/`omitted` with reasons directly; M30 (learning) can pin learned context without
losing history.
