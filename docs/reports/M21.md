# M21 completion report - Capability-safe model router

> **Historical report.** This describes its recorded checkpoint, including old counts
> and limitations. For current status, read [the audit](../AUDIT.md),
> [progress](../../PROGRESS.md) and [known gaps](../../GAPS.md).

## 1. Objective

Route each task to a model that has **demonstrably** got the required capability, never to
one that merely claims it, and make the choice explainable after the fact.

## 2. What was built

* `application/router.py`: `ModelRouter` with capability evaluation, eligibility rules,
  deterministic scoring, decision artefacts, probes and fallback planning.
* Capability states in `managers/models.py`: `verified` / `inferred` / `unverified` /
  `unsupported` / `unavailable`, computed from recorded probes, the runtime baseline,
  declarations and availability - with precedence rules (a failed probe beats a claim).
* `RUNTIME_BASELINE_CAPABILITIES`: what our *code* can do (chat/streaming for the
  llama.cpp, HTTP and scripted adapters), kept separate from model claims.
* `Workspace.runtime_availability`: cheap, no-load availability check per runtime
  (dependency installed, file present, endpoint configured, test double enabled).
* Chat integration: routing decision attached to every reply (`model.routing`), visible
  fallback with `model.failed` / `model.fallback` traces and user-facing warnings.
* Config: `router.require_verified`, `router.allow_unverified_chat`, `router.allow_cloud`,
  `router.prefer_local`, `router.fallback`, `router.max_fallbacks`.
* CLI: `models route`, `models probe`, `models capabilities`.
* Trace kinds `model`/`router`.

## 3. How it was verified

`tests/test_router_m21.py` - 33 tests:

* **states**: adapter capabilities are `inferred`; a passed probe is `verified`; a failed
  probe is `unsupported` and overrides a user claim; the latest probe wins; a missing file
  is `unavailable`; the matrix includes declared, baseline and tested capabilities.
* **probes**: refused for unmeasurable capabilities (`vision`), missing models, and a dead
  endpoint recorded as a failure with history.
* **routing**: unknown capability rejected; "no usable model" explains how to add one;
  simulated model needs the flag; local preferred over remote; remote never chosen without
  `router.allow_cloud`; the consent gate is reported when it is allowed; explicit `--model`
  bypasses the cloud policy but not consent; min-context exclusion; `require_verified`
  flipping decisions before/after a probe; `--allow-unverified` recorded in notes;
  `unsupported` never routed (and `UnsupportedCapabilityError` for an explicit pick);
  decisions traced; preferred model wins ties; fallbacks ranked and excluded for explicit
  choices.
* **availability**: missing `llama-cpp-python` blocks the model with that exact reason; the
  simulated runtime is unavailable without the flag; the check never loads weights.
* **fallback (chat level)**: retryable network failure falls back with trace events,
  warnings and `fallback_from`; a 401 does **not** fall back and is counted as a failure.

Real acceptance: `scripts/acceptance_m21.sh` (transcript in `docs/VERIFICATION.md#m21-acceptance`).
Full suite: **284 passed, 0 failed, 0 skipped** on Python 3.11.2.

## 4. Decisions and their cost

* **Eligibility before score.** The first draft ranked by score and the best-scoring model
  won regardless of whether it could run; the acceptance run caught it routing to a GGUF
  whose runtime is not installed. Eligibility is now a hard filter with recorded reasons,
  and scoring only orders the survivors.
* **`inferred` is not `verified`.** Our adapter implementing chat is a fact about our code,
  not about a model file. It is strong enough by default (otherwise nothing would ever be
  routable offline) but `router.require_verified` makes the distinction observable, and the
  state is printed with its basis everywhere.
* **No fallback on non-retryable errors.** A 401 is a configuration/policy fact; retrying it
  on another provider would hide an auth problem and could leak data to a second vendor.
* **Fallback is loud.** Warnings, trace events and `fallback_from` in the reply. A silent
  substitution is indistinguishable from a working model from the user's point of view.
* **Probes only for measurable capabilities.** `tools` and `json` are probed by inspecting
  the reply; `vision`/`ocr`/audio have no adapter here and are refused rather than
  rubber-stamped.
* **The router does not choose remote models by itself.** `router.allow_cloud` default
  false means an automatic fallback can never be the thing that first sends data off the
  machine; that remains an explicit user act (M20 gates still apply).

## 5. Limitations

* Real model quality is unmeasured: no weights are reachable in this environment. Probe
  results in the transcript come from the labelled test double and are marked as such
  (`simulated: true` in the trace).
* Capability probes are shallow by design (a tiny prompt, a shape check). They prove the
  path works, not that the model is good at the capability.
* `tools` probing only passes when the runtime returns tool calls; no adapter in this build
  emits them yet, so `tools` is effectively unverifiable until M22 lands.
* Fallback does not re-build the context window; it skips candidates whose window cannot
  hold the existing manifest (with a warning) rather than re-planning.
* Cost-aware routing (cheapest adequate model) is not implemented; prices exist (M20) but
  the score does not use them yet.

## 6. What this unlocks

* **M22** can register tools with capabilities and route tool-using turns only to models
  whose `tools` capability is verified.
* **M25** (agent workflows) needs per-step routing decisions that are auditable - it can
  consume `RoutingDecision` directly.
* **M26** (scheduler) can use eligibility to queue work for a model that is actually
  available instead of failing at dispatch.
* **M29** (GUI) gets a ready-made explanation object for a model-picker.
