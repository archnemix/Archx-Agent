# M22 completion report - Tool registry + permission centre

> **Historical report.** This describes its recorded checkpoint, including old counts
> and limitations. For current status, read [the audit](../AUDIT.md),
> [progress](../../PROGRESS.md) and [known gaps](../../GAPS.md).

## 1. Objective

Make tool use possible without making it implicit: a tool declares what it needs, the
permission centre decides whether it may, and the decision plus its outcome is recorded.

## 2. What was built

* `managers/permissions.py` — `CAPABILITIES` (declared, risk-ranked), grants with six
  durations and real scope checking, single-use consumption, time-boxing, revocation,
  approval requests with TTL and queue cap, and one `check()` that every protected
  operation passes through.
* `managers/tools.py` — `ToolSpec` (capability, risk, typed inputs, side effects, dry-run
  support), a registry that validates specs at registration, strict argument validation,
  the fixed execution order, `tool_runs` records (started and finished), trace events, and
  `file_change` auditing for writes and deletes.
* `adapters/local_tools.py` — the sandbox: root-confined file IO, symlink-safe path
  resolution, binary detection, size and output caps, argv-only process execution with a
  minimal environment, timeouts, and a denylist.
* Schema v13 — extends `permission_grants` (usage counting, approval link) and `tool_runs`
  (approval link, dry-run, truncation, sequence) and adds `approval_requests`.
* CLI — `tools list|show|run|runs`, `permissions capabilities|list|grant|revoke|check|prune`,
  `approvals list|show|approve|deny`, with distinct exit codes (4 = refused, 2 = usage).
* Config — `tools.roots`, `tools.max_file_bytes`, `tools.shell_enabled`,
  `tools.shell_denylist`, `permissions.approvals_enabled`, `approval_ttl_minutes`,
  `max_pending_approvals`, `max_grant_hours`; `permissions.default_duration` changed to
  `once`.

## 3. How it was verified

`tests/test_tools_m22.py` — 78 tests in seven groups, plus 13 CLI tests in
`tests/test_cli.py::TestCliTools`:

* **CapabilitiesAndGrants** — every protected tool names a known capability; unknown
  capabilities list the known ones; scoped durations require their context; the default
  duration is single-use and is consumed (counted, marked `system:consumed`); conversation,
  task and project grants are scope-checked *and* do not apply without that context;
  wildcard subjects work; a grant for one capability never allows another;
  `permissions.denied_capabilities` beats a grant; time-boxed grants expire and `prune`
  revokes them; `--for` is bounded; `persistent` without `--confirm` is refused; a revoked
  grant stops allowing; a missing grant is `NotFoundError`.
* **Approvals** — one request per operation (deduplicated), approval mints exactly the
  requested capability, double approval is refused, `approve()` has no widening parameter,
  denial creates no grant and the next attempt makes a new request, expired requests are
  listed as expired and cannot be approved, the queue cap and the "approvals disabled" mode
  both deny with a reason, `check` creates nothing, and an approval for one subject does not
  cover another.
* **Registry** — built-ins are listed with risk/dry-run/protection, unknown tools, duplicate
  registration and unknown-capability specs are refused, unknown arguments name the
  accepted ones, missing arguments are named, string integers are coerced and wrong types
  refused, dry-run on a non-previewable tool is refused.
* **FileTools** — write denied until approved (file absent) then created; hashes reported;
  previous hash on overwrite; append; dry-run writes nothing; read window/sha/lines; binary
  refusal; missing file is a failed run; listing with kinds; delete needs its own capability
  and supports preview; traversal, absolute-outside, symlink escape refused; size cap;
  directory delete refused.
* **ShellTool** — grant required then real execution; non-zero exit is a failed run with
  the code; timeout kills (`timed_out`); denylist cannot be approved; missing program is a
  clear error; a child process does not inherit secrets; `;` is not a shell operator; cwd
  outside the roots refused.
* **RunsAndTrace** — denials recorded with the approval id; run sequence monotonic and
  ordered; a single-use grant is consumed even when the tool fails; unprotected tools need
  no grant; dry runs are recorded; `file_change` carries the hash; permission decisions are
  traced both ways; tool_call events record outcomes; context reaches the check; the
  registry counts active grants; state survives a reopen.
* **Authority** — a tool cannot pass itself a `capability` argument, `ToolManager` has no
  grant API, specs are frozen, and a denial leaves no grant behind.

Real acceptance: `scripts/acceptance_m22.sh` (transcript in
`docs/VERIFICATION.md#m22-acceptance`) — real files, real subprocesses, real timeouts.
Full suite: **381 passed, 0 failed, 0 skipped** on Python 3.11.2.

## 4. Decisions and their cost

* **The default duration is `once`.** The first draft defaulted to `task`, which cannot be
  scoped when there is no task - the first real run failed with "a task grant needs a task".
  A single-use default is the only one that is both usable without context and safe.
* **No silent downgrade for `persistent`.** The first draft shortened a `persistent` grant
  to the default when `--confirm` was missing. That is exactly the kind of quiet
  substitution this project avoids: it now refuses and says what is missing.
* **The run row exists before execution.** `tool_runs` is written with status `running`
  before the work and finished afterwards, so a crash leaves evidence of the attempt
  instead of nothing. Sequence numbers come from `MAX(seq)+1` inside the write transaction.
* **A single-use grant is spent before the work.** Otherwise a failing tool would return a
  grant the user thought had been used.
* **Execution errors close the run and re-raise.** A missing file is an exception *and* a
  `failed` row; a command that ran and exited 1 is a `failed` run without an exception. The
  distinction is "could not complete" versus "completed, unsuccessfully", and both are
  visible.
* **The denylist is checked before the permission check.** A denied-by-policy program
  cannot consume a grant and cannot be approved - it produces a refusal with no approval id.
* **Approvals cannot be widened.** `approve()` takes no capability/subject/scope argument.
  Widening authority requires `permissions grant`, which is a different, visible act.
* **No shell.** `shlex.split` + argv, so quoting mistakes fail loudly instead of creating a
  second command line nobody reviewed.

## 5. Limitations

* No tool-calling loop: a model cannot yet ask for a tool. M25 connects the chat path to
  this registry.
* `net.fetch` is declared but no tool implements it, so it can only ever be refused.
* No recursive directory deletion, no pipelines, no background processes, no PTY.
* Approvals are decided out-of-band (`approvals approve`) and a run must be repeated; there
  is no suspend/resume of an in-flight workflow (that arrives with tasks in M24/M25).
* `shell.run` can still run anything on the PATH that is not denylisted - the grant is the
  control, not a syscall sandbox. This is stated rather than overstated.
* Windows paths are untested.

## 6. What this unlocks

* **M23** (MCP + extensions): discovered tools register with an origin and trust level and
  go through the same `check()`; an extension cannot self-grant because the only writer of
  grants is the permission centre.
* **M24** (task history): `task_id`-scoped grants and `tool_runs.task_id` already exist, so
  replay can answer "which tool needed which permission" for a task.
* **M25** (agent workflow): the execution order, refusal taxonomy and run records are the
  contracts a loop needs; nothing has to be re-invented for subagents.
* **M26** (scheduler): `tool_runs` duration/status feed resource accounting.
* **M31** (coding workspace): `fs.*` + `file_change` traces are the audit trail for edits.
