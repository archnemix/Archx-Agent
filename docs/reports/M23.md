# M23 completion report - MCP client/server + extension foundation

## 1. Objective

Let external tools in without letting them in *on their own terms*: a server or extension
is a record until the user trusts it, its tools are ordinary registry entries, and every
call passes the same permission centre as a built-in tool.

## 2. What was built

* `adapters/mcp_client.py` — JSON-RPC 2.0 client with two transports: `stdio` (spawned
  process, line-delimited messages, captured stderr, killed on close) and `http` (POST,
  JSON or SSE responses, `Mcp-Session-Id` handling). Deadlines on every request, answers to
  server→client requests, explicit protocol errors.
* `managers/mcp.py` — server records (transport, command/url, env/header *keys*, trust,
  enabled), discovery, tool registration as `mcp.<server>.<tool>` with capability
  `mcp.call`, and `restore()` so a trusted server's tools are back after a restart.
* `interfaces/mcp_server.py` — optional MCP server exposing a whitelist of Archx tools over
  stdio or HTTP, with a distinct permission subject (`mcp-server`).
* `adapters/extension_runtime.py` — runs an extension program with a rebuilt environment,
  one JSON request in, one JSON response out, with a timeout and output caps.
* `managers/extensions.py` — manifest validation, install/trust/enable/remove, tool
  registration as `ext.<extension>.<tool>`, and the `restore()` seam.
* `ToolManager` grew the seams this needed: `register_handler`, `declare_spec`,
  `unregister_spec`, `permission_subject`, and `json`/`float` input kinds.
* New capabilities: `mcp.call` (medium) and `process.exec` (high).
* Schema v14 — MCP server/tool columns, extension trust columns and `extension_tools`.
* CLI — `mcp servers|add|show|enable|disable|trust|untrust|remove|sync|tools|call|serve`
  and `extensions list|install|show|trust|untrust|enable|disable|remove|tools|call`.
* Settings — `mcp.client_timeout_seconds`, `mcp.server_tools`, `extensions.enabled`,
  `extensions.directory`.
* `docs/MCP.md`, M23 acceptance script, and a real fixture server
  (`tests/fixtures/mcp_server.py`) used by both tests and acceptance.

  endpoint, invalid URL and invalid body.

  (discovered, nothing registered, reason), trusted+enabled sync (registered specs with

  argument coercion from the remote schema, a dropped tool being unregistered, untrust and

  status counts, idempotent re-sync, and an HTTP server synced end to end.
* **Archx MCP server**: refuses to start while disabled, whitelist enforced (both listing

Real acceptance: `scripts/acceptance_m23.sh` (transcript in

## 4. Decisions and their cost

* **Trust, enable and permission are three different things.** The first draft coupled
  trust to registration, which made "show me what this server offers" impossible without
  handing it authority. Discovery is now always allowed; registration needs trust *and*
  enable; calling needs a grant.
* **Registered tools are restored from the database on open.** Without it, a CLI command
  would have to re-run `sync`, and worse, the registry would disagree with what `mcp
  servers` reports. The *decision* is durable; the *spec* is rebuilt.
* **The MCP server uses a different permission subject.** `mcp-server` is not `fs.read`.
  This is what stops a local grant from silently authorising a remote client, and it is
  demonstrated in acceptance by a denial *after* the client was already approved.
* **A whitelist, not the registry.** Exposing `fs.write` because it exists would make the
  server a remote-control surface. The default list is read-only.
* **`argv[0]` is a program, everything else is data.** The first validation refused
  `/usr/bin/python3` as "outside the extension", which made every real extension
  impossible. The trust decision covers the interpreter; the manifest is not allowed to
  ship file arguments pointing out of its directory.
* **No shell, again.** Extension and MCP stdio programs are executed with argv arrays and a
  rebuilt environment (MCP servers inherit the environment, since they legitimately need
  their own credentials - documented, and the difference is deliberate).
* **`--command` needed a different argparse dest.** It collided with the top-level
  `command` attribute, so the handler lookup failed and the CLI printed help. Recorded in
  the decision log because it is an easy mistake to repeat.
* **`config set` now parses lists.** `config set mcp.server_tools '[a,b]'` silently stored a
  string, which made the server reject a list of single characters. List settings accept
  JSON arrays or comma-separated values, and malformed JSON is a usage error.

## 5. Limitations

* Our MCP **server** has no authentication and binds loopback; it is not for remote hosts.
* No OAuth/dynamic registration for HTTP MCP servers; static headers only.
* Sampling, elicitation, prompts and server-initiated notifications beyond `ping` are not
  implemented.
* No manifest signing. The hash makes an unexpected change visible; it does not prove
  authorship.
* An extension tool's capability gates the call, not every syscall of its process. A
  trusted extension is an ordinary process on the machine.
* MCP tool results are converted to text/`structuredContent`; binary content is
  JSON-serialised rather than stored as an attachment (M34 will need this).

## 6. What this unlocks

* **M24** can record which MCP/extension tools a task used and reproduce the calls.
* **M25** (agent workflow) can offer these tools to a model knowing each is a registry
  entry with a capability: the loop needs no special case for "external" tools.
* **M26** (scheduler) can treat slow MCP calls as jobs with timeouts already enforced.
* **M29** (GUI) can show the trust/enable/grant triangle as three toggles with the same
  semantics as the CLI.
* **M40** (hardening) has a concrete trust boundary to attack: manifests, servers, and the
  subject separation.
