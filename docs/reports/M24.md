# M24 completion report - task history, content versions and reproduction

> **Historical report.** This describes its recorded checkpoint, including old counts
> and limitations. For current status, read [the audit](../AUDIT.md),
> [progress](../../PROGRESS.md) and [known gaps](../../GAPS.md).

## 1. Objective

Make work on this machine explicable after the fact: what was done, in what order, what it
produced, what state that output was in the last time anyone looked, and whether the work
could be run again. Without it, every later milestone (agents, jobs, GUI) would invent its
own history, and "reproducible" would be a claim with no record behind it.

## 2. What was built

* `managers/tasks.py` - `TaskManager`: create/start/complete/fail/cancel with final
  terminal states, a `task_log` timeline ordered by sequence, parent/child trees, open
  questions, filters, statistics, artifact attachment with checksum + content version, and
  `interrupt_stale()` which distinguishes a dead owner from a live one and from a manually
  tracked task.
* `managers/versions.py` - `VersionManager`: append-only content history per
  (subject type, subject id), deduplication by checksum, explicit labels, ordinals,
  unified diffs, restore-as-new-version, binary/large content recorded as checksum-only.
* `managers/reproduction.py` - `ReproductionManager`: environment capture, fidelity
  (`exact`/`partial`/`impossible`) derived from evidence, replay commands built from the
  real tool-run arguments and the message that started the turn, recording, and `verify()`
  which recomputes everything and reports what changed.
* Chat integration: every turn is a task (`tasks.auto_record_chat`), created before the
  model call, completed after the reply is stored, marked failed with the error otherwise;
  `send(task_id=...)` attaches a turn to an existing task.
* Tool integration: a run inside a task is linked to it, appears in `tasks show`, and is
  logged on the timeline - including refusals.
* CLI: `tasks list|show|start|queue|complete|fail|cancel|log|question|resolve|artifacts|
  attach|reproduce|stats` and `versions list|record|show|diff|restore|subjects`.
* Schema v15: `task_log`; `version_records.ordinal/size/restored_from/content_stored`;
  `reproduction_records.app_version/recorded_by`; indexes. `51` tables.
* Settings: `tasks.enabled`, `tasks.auto_record_chat`, `tasks.interrupt_stale_on_open`,
  `tasks.max_version_bytes`.
* `docs/TASKS.md`, `scripts/acceptance_m24.sh`.

## 3. How it was verified

`tests/test_tasks_m24.py` - **75 tests**, in the order the milestone was built:

* **lifecycle** (15): queued vs running, start-twice conflict, completion with resources and
  outputs, terminal states are final (complete/fail/cancel all refused afterwards), failure
  records the exception type and truncates, cancel keeps the reason, unknown type and
  unknown parent rejected, title normalisation, **ordering by insertion sequence when five
  tasks share a millisecond**, filters, children/tree, questions (dedupe, index and text
  resolution, both errors), log sequence, statistics.
* **interruption** (5): sweep only touches running tasks, reopening the workspace marks a
  task whose owner is gone as interrupted (with the warning), manual tasks are never swept,
  a task owned by a live process is left alone (a real `sleep` subprocess), the sweep can be
  disabled.
* **artifacts** (6): checksum/size/MIME/relative path, attachment inside vs outside the
  home, missing file, re-attach creates the next content version, versioning can be skipped,
  a deleted file is reported `MISSING` without touching the user's data, a missing artifact
  is a `Result` error.
* **versions** (15): ordinal and size, identical content is not a version, next ordinal on
  change, label collisions, subject validation, exactly-one-source, text vs binary files,
  oversized content refused with the setting named, checksum-only recording, latest/at/
  history, unknown version lists the known ones, diffs (default base, explicit base,
  identical), restore keeps history and records `restored_from`, subject aggregation, and
  persistence across a reopen.
* **reproduction** (14): exact for a deterministic tool task, simulated model is a caveat,
  removed model makes it impossible, missing tool impossible, failed task partial,
  interrupted task cannot claim an outcome, open questions are a caveat, deleted output
  blocks reproduction, commands contain the real `fs.read path=notes.txt` invocation,
  capture/list/get/stats, verify unchanged, verify notices a removed model (`partial` ->
  `impossible`, new blocker), verify notices changed settings, untrusted dynamic tool is a
  blocker.
* **integration** (6): a chat turn becomes a completed task with conversation, model, input
  reference, output reference and resource use; a failed turn becomes a failed task; auto
  recording can be disabled; an explicit task is reused rather than duplicated; a tool call
  lands on the task's timeline; a **denied** call is recorded on the task too.
* **CLI** (9): start/log/complete/show (both human and `--json`), queue/cancel, fail +
  question/resolve, attach + versions list/diff/restore through the installed console
  script, prompt versions and subjects, reproduce (`--record`), reproduce of a removed model
  exits **3**, chat appears in the history, unknown task is a clean error, `db check`.

Full suite: **543 passed, 0 failed, 0 skipped** on Python 3.11.2.

Real acceptance: `scripts/acceptance_m24.sh` (transcript in

## 4. Decisions and their cost

* **A task is created before the model call, not after the reply.** A record written only on
  success cannot explain a failure. The cost is a task row and two lines in the timeline for
  a call that fails; the benefit is that a failed turn is visible with its error.
* **`interrupt_stale` uses an owner (instance + pid), not a timestamp.** A timestamp would
  make a long task look dead and a crashed task look alive. Manual CLI tasks are exempt
  because the CLI process exits immediately by design - sweeping them would destroy the
  user's own bookkeeping. A task owned by another live process is left alone and reported.
* **Versioning is append-only; restore writes a new version.** Editing history would make
  "what did it look like at 10:41" unanswerable. The cost is that restoring creates a row;
  the benefit is that the divergence itself is recorded.
* **Unchanged content is not a version.** Otherwise every save (or every re-attached
  artifact) would produce a row and the diff would be noise.
* **Large content is not truncated into the version store.** Explicit content above the
  limit is refused (there is nowhere else to keep it); file content above the limit records
  a checksum only (the file still exists). Never a half-document that looks complete.
* **Fidelity is computed from evidence, never asserted.** `exact` requires the model to be
  present and deterministic, every tool to exist, and no open question or consumed
  single-use grant. A simulated model is therefore always at most `partial` - the test
  double performs no inference, so claiming it reproducible would be false.
* **Reproduction records commands, not a re-run.** Re-running belongs to workflows and jobs.
  The commands are built from the recorded arguments, which is why running one of them is a
  fair test of the record.
* **Artifacts are references.** Copying outputs into the database would double storage and
  break the user's own file layout. The checksum makes "the file changed" detectable.

## 5. Limitations

* `tasks reproduce` does not execute the task; only M25/M26 can do that, and they will build
  on the same record.
* Version content is stored in the write journal as well as the version row (the journal
  must be replayable), so a 1 MiB version costs about 2 MiB on disk. Raising
  `tasks.max_version_bytes` raises that cost.
* No garbage collection for task/version history yet; it is append-only by design and M40
  will decide retention.
* The artifact MIME type comes from the file extension.
* A task's `tools` list is the set of tools it used, not a declared plan - plans arrive with
  M25.
* Python 3.13 was still not available in this environment (`tests` verified on 3.11.2).

## 6. What this unlocks

* **M25** (agent workflows) gets the durable shape of a task and the "attach a chat turn to
  an existing task" seam; subagents become child tasks with the same timeline.
* **M26** (scheduler) can record jobs as tasks and reuse the interruption rule for killed
  workers.
* **M27/M29** (Simple Mode, GUI) can list history and show a task without a new API.
* **M31** (coding workspace) can version files and attach them to tasks with diffs already
  available.
* **M40** (hardening) has a real reproduction check to run against the release.
