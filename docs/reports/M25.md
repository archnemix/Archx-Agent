# M25 completion report - agent workflows (user-directed and AI-directed)

> **Historical report.** This describes its recorded checkpoint, including old counts
> and limitations. For current status, read [the audit](../AUDIT.md),
> [progress](../../PROGRESS.md) and [known gaps](../../GAPS.md).

## 1. Objective

Turn "the assistant can call one tool" into "the assistant can carry out a plan", without
inventing a second permission system, a second history or a second chat path. A workflow is
data; the application executes it through the machinery that already exists and records what
happened.

## 2. What was built

* `managers/workflows.py` - the workflow **definition format** (six step kinds), strict
  validation (unknown fields, unknown kinds, missing inputs, unknown tools, step caps),
  template parsing/rendering (`{{goal}}`, `{{step.N.output}}`, `{{input.NAME}}`), the
  `WorkflowManager` (records, statuses, ordered step rows, statistics) and two built-in
  user-directed templates.
* `application/agent.py` - `AgentRunner`: executes a stored workflow step by step, with
  budgets (steps, wall clock, tokens, subagents), cancellation re-read between steps, a
  checkpoint gate checked **before** anything runs, subagents as child tasks with their own
  conversation, and the planner (`AgentRunner.plan`) that asks a model for JSON and refuses
  anything that is not a valid, registered-tool plan.
* Chat and tool integrations: model steps go through `ChatService.send` (routing, fallback,
  usage, tracing, task linkage); tool steps go through `ToolManager.execute` (capability,
  grant/approval, run record, task timeline).
* CLI: `agent plan|list|show|run|run-file|run-template|templates|approve|reject|cancel|rerun|steps|stats`.
* Schema v16: `workflows` and `workflow_steps` (53 tables).
* `scripts/openai_protocol_stub.py` grew `--reply-file`, so acceptance can drive a real HTTP
  round trip with a canned plan.
* `docs/AGENTS.md`, acceptance script.

## 3. How it was verified

`tests/test_agent_m25.py` - **60 tests**:

* **definition format** (20): normalisation, unknown workflow field, name required and
  bounded, unknown mode, empty steps, unknown kind, each kind's required input, unknown step
  field, nested steps only on subagents, args/metadata shapes, tool must exist, step cap,
  nested steps counted, memory limit bounds, derived titles.
* **templating** (5): substitution, unknown variable lists what exists, container walking,
  `{{input.*}}` substitution that leaves run-time placeholders alone, missing input named.
  Plus every built-in template validated against the live registry.
* **execution** (15): model+note completion with task, timeline and conversation; tool step
  recorded with the run's task id; denied tool fails the run with an approval id and the
  recovery path after approval; `continue_on_error`; memory step using the memory systems;
  subagent child task + separate conversation + aggregated tokens; nesting limit; checkpoint
  refusal *before* anything runs and success with `--approve`; finished workflow cannot run
  twice; unknown workflow; lookup by name; listing and stats.
* **budgets and cancellation** (7): step cap, wall clock, token budget (15 long prompts),
  a cancel issued from inside a step stops the next one, cancelling before a run, reject and
  cancel terminal, approving a non-proposed workflow is a conflict.
* **planner** (6): a real HTTP model returns a plan -> stored `proposed`, refused without
  approval, runs with it; prose around the JSON tolerated; a reply without JSON stores
  nothing and fails the planning task; a plan naming a missing tool is refused; approving a
  plan does **not** grant a capability (the write still needs `fs.write`); empty goal refused.
* **installed console script** (6): `run-file` end to end (tool + model) with `agent list`,
  `show`, `stats`; broken JSON is a usage error; checkpoint exits **4** and passes with
  `--approve`; a full `agent plan` -> run-without-approval (exit 4) -> `--approve` round trip
  against the HTTP stub; templates with `--input` including the missing-input error; approve
  and reject commands.

Full suite: **603 passed, 0 failed, 0 skipped** on Python 3.11.2.

Real acceptance: `scripts/acceptance_m25.sh` (transcript in

`db check`.

## 4. Decisions and their cost

* **A workflow is data, never code.** There is no expression language and no shell shortcut:
  if a step needs to touch the machine it names a registry tool and the permission centre
  decides. The cost is that complex logic needs more steps; the benefit is that a plan file
  cannot carry its own authority.
* **Model steps use the ordinary chat path.** Reusing `ChatService.send` means routing,
  fallback, context and usage accounting are identical to a chat turn; the cost is that a
  workflow needs a conversation (which turns out to be useful - it is the transcript).
* **A checkpoint is an up-front gate, not a mid-run pause.** Refusing before the run starts
  means an approved re-run cannot repeat a side effect from an earlier partial attempt.
  Durable pause/resume needs jobs with hard timeouts (M26), so it is explicitly deferred.
* **Budgets are checked between steps.** Killing a thread mid-call is unsafe; between steps
  is the last clean point, and the failure names the budget that was exceeded.
* **A failed run is terminal; `rerun` creates a new record.** Rewriting a failed record into
  a successful one would erase the failure. A visible new run with `replaces` keeps both.
* **Subagents are child tasks with their own conversations.** Separate contexts prevent a
  subagent from flooding the parent's window, and the task tree makes the delegation visible.
  Nesting is capped at two levels because unbounded recursion is a cost amplifier.
* **The planner refuses rather than repairs.** No JSON, invalid JSON, unknown tool, unknown
  field: nothing is stored and the planning task records the failure. A "helpful" repair
  would mean executing a plan the model did not write.
* **Approving a plan is not approving its capabilities.** This is demonstrated in the tests
  and acceptance: an approved plan still stops at `fs.write` with an approval id.

## 5. Limitations

* Sequential steps only; no loops, branches or retries (M26/M39).
* No durable pause/resume: a failed run is re-run from the start.
* Step output is truncated to 8,000 characters for templates and 20,000 for storage; a step
  that needs a large document must write it to a file and pass a path.
* Subagents share the parent's process and budgets; true isolation is M26.
* The planner's quality is the model's quality. With the protocol stub or the simulated test
  double the plan is not useful - the acceptance says so rather than pretending otherwise.
* Python 3.13 still unavailable in this environment.

## 6. What this unlocks

* **M26** (scheduler) can run workflows as jobs with concurrency, hard timeouts and durable
  resumption; the workflow/step records are already the right shape.
* **M27/M28** (Simple Mode, Researcher Mode) are workflows with domain-specific steps.
* **M29** (GUI) can show a plan, approve it and watch steps complete.
* **M31** (coding workspace) can express read/edit/test/commit as a workflow with the
  version and task records from M24.
* **M40** (hardening) has a second trust boundary to attack: a plan file that tries to
  widen authority.
