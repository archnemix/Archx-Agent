# M26 completion report - resource and job scheduler

## 1. Objective

Make long work survivable. Before this milestone the app could run a workflow, but only
inside the process that asked for it: close the terminal and the work was gone, and a step
that hung held the process forever. The milestone asked for concurrency, hard timeouts,
durable jobs and pause/resume. The constraint that shaped every decision was *do not build
a second task store*: the queue had to sit on the M24 task history and the M25 workflow
records, not beside them.

## 2. What was built

* **`managers/jobs.py` - the queue as data.** `JobManager` over the `jobs` table, extended
  (schema v17) with `attempts`, `max_attempts`, `timeout_seconds`, `pid`, `worker`,
  `requeued_at`, `control`, `cursor` and `dedupe_key`. Priorities (0-9), a `queue_seq`
  assigned inside the enqueue transaction, per-job resource estimates, idempotent submission
  via `dedupe_key`, and a real state machine over
  `queued | running | paused | completed | failed | cancelled | interrupted`.
* **Claiming is one transaction.** `claim()` selects the best fitting queued row and marks
  it running in a single journalled write, so two workers cannot own the same job. It also
  supports `claim(job_id=...)` for "run this one now".
* **Hard deadlines.** A deadline is computed at claim time and stored. The runner enforces
  it (SIGKILL to the child's process group for a `command`, a step-boundary check for a
  `workflow`), and every workspace open calls `reap_expired()` so a deadline that passed
  while nothing was running becomes a `failed` row instead of a permanent `running` one.
* **Crash recovery.** `recover()` requeues a `running` job whose pid is dead while attempts
  remain, and marks it `interrupted` when they do not. It never invents a completion.
* **`application/scheduler.py` - the runner.** `JobRunner` with two real kinds:
  `command` (a child process in its own session, capturing exit code, stdout, stderr,
  duration and env overrides) and `workflow` (an M25 workflow through `AgentRunner`).
  `drain()` runs up to `scheduler.max_concurrent_jobs` at once and claims a job only when
  its declared estimate fits what is left of `scheduler.cpu_limit_percent` /
  `scheduler.memory_limit_mb`.
* **Pause and resume, end to end.** `AgentRunner.run(..., resume=, control=)` gained a
  control hook called at each step boundary and a resume path that skips steps with a
  succeeded row, reusing their outputs. `RunPaused` is a *clean stop*, not a failure: the
  workflow stays `running`, the task stays open and the job records its cursor.
  `TaskManager.interrupt_stale(protect=...)` plus `JobManager.protected_task_ids()` stop the
  crash sweep from closing a task a paused or resumed job still owns.
* **One history.** Every job writes its milestones to the task timeline
  (`job_started`, `command_succeeded`, `job_paused`, `job_resumed`, `job_completed`, ...) and
  traces them under the existing `task` kind. There is no second task table and no second
  log.
* **CLI.** `jobs submit command|workflow`, `list`, `queue`, `show`, `logs`, `run`
  (`--once`, `--max-jobs`, `--max-seconds`, `--concurrency`, `--kind`), `pause`, `resume`,
  `cancel`, `retry`, `stats`, `recover`, `reap`, with `0/1/2/3` exit codes that distinguish
  "finished", "something failed", "bad usage" and "work remains".
* **Schema v17**, config keys under `scheduler.*`, `docs/SCHEDULER.md`, and
  `scripts/acceptance_m26.sh` (23 self-checking assertions).

## 3. How it was verified

* **Unit and integration: 94 tests** in `tests/test_scheduler_m26.py`
  (88 test functions, several parametrised), covering enqueue validation, ordering, dedupe,
  claiming (including six threads racing over 24 jobs), command jobs (success, non-zero
  exit, missing binary, bad payload, bad cwd, env overrides, truncation, timeout, cancel,
  pause refusal), workflow jobs (completion, missing ref, unapproved plan, refused tool,
  pause, resume without replay, resume after a swept task, cancel, deadline), pause/resume/
  retry transitions, recovery and reaping, concurrency and admission limits, the installed
  console script, schema/config, and boundary cases (expired() only while running, attempts
  never negative, dedupe ignores interrupted jobs, a stopped runner claims nothing).
* **Full suite: 697 passed, 0 failed, 0 skipped** (Python 3.11.2, 140.6s; junit xml:
  `tests=697 failures=0 errors=0 skipped=0`).
* **Real acceptance** (`scripts/acceptance_m26.sh`, exit 0, 23/23 checks): concurrency
  measured by wall clock, a `sleep 30` killed in about a second with no process left behind,
  a workflow paused by a second process and resumed by a third with every step run exactly
  once, a worker `SIGKILL`ed mid-job and the job recovered on attempt 2, and an ungranted
  `fs.write` step failing the job without writing a file. Transcript:
  `docs/VERIFICATION.md#m26-acceptance-transcript`.

## 4. Decisions and their cost

* **The queue is a table, the history is the task.** A job has no `job_log`; its milestones
  go to the task timeline. The cost is that a job which never ran (still queued) has no
  task and therefore no timeline - it is described by its own row plus trace events. The
  benefit is that "what happened" stays answerable in one place.
* **Retries are for crashes only.** A failed or timed-out job keeps its error; `jobs retry`
  is explicit. Automatic retry of side effects is not a scheduler's call. The cost is that a
  transient failure needs a human (or an automation) to retry it.
* **Deadlines do not pre-empt in-process steps.** A child process is killed; a workflow step
  that is already running finishes. Killing a thread mid-write is worse than a late
  deadline. `GAPS.md` says so.
* **A running command refuses `pause`.** Freezing a process and its children is not a state
  the rest of the system can reason about. The refusal names the reason and points at
  `cancel`.
* **Paused work owns its task.** `protected_task_ids()` keeps the crash sweep off tasks a
  paused/resumed job will continue. Without it, resume produced a duplicate task and looked
  like a crash - the acceptance run showed exactly that before the fix.
* **`jobs run` exits 3 when work remains.** "The command succeeded" and "the queue is empty"
  are different facts; conflating them would hide a paused or blocked job.
* **Estimates, not cgroups.** Resource admission uses the estimate the job declares and
  records observed duration/peak RSS afterwards. It prevents oversubscription by arithmetic;
  it does not enforce a memory ceiling in the kernel.

## 5. Limitations

* A hung step inside an in-process workflow is bounded only at step boundaries; the deadline
  cannot interrupt a model call that never returns. `GAPS.md` records this.
* No CPU/memory cgroups: the memory budget is advisory. Peak RSS is recorded for this
  process, not per job.
* One scheduler per process; there is no daemon. Running `jobs run` in two terminals is
  safe (claims are transactional) but neither process knows about the other's shutdown.
* Child processes keep running if the worker is `SIGKILL`ed (the job is recovered and
  re-executed; the orphan is left to finish on its own).
* Pause granularity is a workflow step, not a line of a command. Only `workflow` jobs can be
  paused mid-run.
* No scheduling times (`not_before`) or cron expressions yet - that arrives with M39
  automations, on top of this queue.

## 6. What this unlocks

* **M27-M33** (Simple/Researcher/Learning/Coding/Experimental/Play modes) can submit long
  runs and let the user close the app.
* **M36 training** and **M37 remote compute** can use the same queue and deadlines rather
  than inventing a second one - a training run is a job whose kind registers its own runner.
* **M39 automations** can create jobs on a schedule without a new execution path.
* **M40 hardening** has the crash matrix it needs: the acceptance script already kills a
  worker mid-job and asserts the queue recovers.
