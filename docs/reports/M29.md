# M29 completion report - GUI core workflows

## 1. Objective

Twenty-eight milestones produced one interface: a CLI with thirty commands. That is an
honest interface for the person who built it and a wall for everyone else - and the wall is
not the typing, it is the mental model. "Which command shows me whether anything is waiting
for my decision?" is a question the app should answer by showing the thing.

M29 asked for the primary workflows in a GUI with **no placeholder controls**. The second
half of that sentence is the whole milestone. A GUI is where honesty gets expensive: a
greyed-out button, a fake spinner, a "Settings" tab that saves nothing, a second code path
that skips the permission centre "just for the UI". Each is small, and each turns the product
into a demo of itself.

So the milestone was defined as: **the GUI is a client**. Same managers, same services, same
refusals, no new tables. What the browser shows is what the database says, and what the
browser does is what the CLI would do.

## 2. What was built

* **`interfaces/gui/server.py` - `GuiApi`.** Twenty-two routes over the real application:
  status, models, conversations, chat, search, memory, tasks, jobs, approvals, permissions
  and research. `dispatch()` is a plain function of a `Request`, so 80 tests drive it without
  opening a socket; `GuiServer` is the thin `ThreadingHTTPServer` around it.
* **One authentication gate.** A random per-process token, compared with
  `hmac.compare_digest`, accepted as `?token=`, `Authorization: Bearer`, `X-Archx-Token`, or
  exchanged at `POST /api/session` for an `HttpOnly; SameSite=Strict` cookie whose value is
  an HMAC of the token (the browser never holds the key; a restart invalidates every cookie).
  Twenty bad attempts a minute → `429`.
* **A structural CSRF boundary.** Cookie-authenticated writes must carry
  `X-Archx-Request: gui`; `OPTIONS` returns 405; no `Access-Control-*` header is ever sent.
  A cross-site page can neither set the header (no successful preflight) nor read the
  responses, and `SameSite=Strict` means the cookie is not sent in the first place.
* **A page with no build step.** One HTML file, one stylesheet, one script, no framework, no
  CDN, `script-src 'self'`, no inline handlers, no `eval`. Assets are served by exact file
  name from package data, so `../server.py` and `%2e%2e%2f` are 404s.
* **`archx-agent gui serve` / `gui routes`.** The banner prints the home, the bind, the token
  and the URL, and flushes (a piped stdout is block-buffered - a token nobody can see is not
  a token). A non-loopback bind without `--allow-remote` exits 2 and says why.
* **Config:** `gui.host`, `gui.port`, `gui.allow_remote`, `gui.open_browser`,
  `gui.session_minutes`, `gui.max_body_bytes`.
* **`docs/GUI.md`** and **`scripts/acceptance_m29.sh`**: 46 checks against a real socket,
  including a real web-research run through an approval granted in the page.

## 3. What the GUI deliberately does not have

No settings tab that writes nothing, no disabled "Train" button, no fake progress. The panels
are exactly the features that exist (status, chat, research, search, tasks, jobs, access,
memory, models). When a panel cannot act it shows the same refusal text as the CLI and the
command that would unblock it - for example the status panel lists "No model is registered"
with the `models add-http` line, and a web research request returns 403 with the approval id.

Workflow *authoring* is not in the GUI (it is a real feature, M25, and a plan editor is not a
panel), and neither is token-by-token streaming. Both are recorded in GAPS rather than
implied by an empty control.

## 4. How it was verified

* **85 tests** in `tests/test_gui_m29.py`: routes and their docs, the auth matrix (no token,
  wrong token, bearer, header, query, cookie, forged cookie, restart invalidation, rate
  limit), CSRF in both directions, no CORS headers, the status counts against the managers,
  chat (task recorded, conversation continuity, oversize message refused before it is
  stored), search notes, memory (store, duplicate 409, invalid kind), tasks (list/detail/
  timeline), jobs (queue, drain a real command, pause/resume, cancel, unknown action), access
  (approve mints one grant, deny mints none, double approve refused, revoke), research (a
  local run with labels and verification, the raw report endpoint, web without a grant → 403
  naming the approval, no URLs → 400), assets (exact names only, no absolute URLs, no inline
  handlers, security headers, framing allowed), and the socket layer (headers without the
  interpreter banner, HEAD, bad JSON, 413 before reading, cookie round trip, 20 concurrent
  reads, port closed on stop).
* **984 tests** in the full suite, 0 failures, 0 skipped (190 s).
* **`scripts/acceptance_m29.sh`**: 46 checks, exit 0.

## 6. Bugs the milestone found (and fixed)

* `POST /api/session` was refused by the CSRF gate itself: the check ran before the session
  route. The browser always sends the header, but the ordering was wrong; preflight-style
  checks now run first only for state-changing requests that are *not* the session exchange.
* The cookie was compared against the raw token, so a valid session could never authenticate
  a read. Found by the acceptance script's "cookie opens a read" check, not by a unit test -
  which is why that check exists.
* `GET /api/tasks/{id}` checked `is_err` on a value that is a `Task`, not a `Result`: a 500
  for every task detail. The GUI-wide test caught it because it asked for the detail the page
  asks for.
* `HEAD /` returned 401: the `HEAD` verb fell through to the API branch instead of the static
  branch, so a monitoring probe saw an auth error on a public page.
* The banner was block-buffered when stdout was a pipe, so `gui serve` printed nothing until
  it exited - invisible under a script, a log or a preview.
* Two acceptance checks in the first draft asserted against JSON instead of the socket
  (`the port is closed`), which is the same class of mistake M28 made with exit codes.
* The memory panel offered six kinds (`episodic`, `semantic`, `procedural`, `working`,
  `preference`) that `MemoryManager` does not have - it accepts `active`, `permanent`,
  `archival`, `project`, `solution`, `learning`. Every store from the page would have been a
  400. It was found by seeding a demo home, not by a test, so the fix came with a test that
  reads the dropdown out of the HTML and compares it with `managers.memory.KINDS`.

## 7. Deliberate limits

Recorded in [GAPS.md](../../GAPS.md) and [GUI.md](../GUI.md): a web page rather than a native
window, one token for one user, no accounts or per-person audit, no workflow authoring and no
plan approval, no streaming, one home per process, no TLS, and no defence against a local
process that can already read the database.

## 8. Next

M30 (Learning Mode) should reuse the pattern that worked here: a record for the goal, a task
for the session, and a refusal when a step needs something the user has not granted. The GUI
then picks it up for free - a new panel and one route, not a second implementation - which is
the test of whether M29's boundary was drawn in the right place.
