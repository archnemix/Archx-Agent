# M30 completion report - Learning Mode

## 1. Objective

A tutor is the friendliest place in a personal AI app to put a comfortable lie. Five
sentences cost nothing and mean nothing:

* "Great job! You clearly understand WAL mode now."
* "Correct — 9/10."
* "Here's the answer." (before any attempt)
* "You'll see this again in three weeks." (for no stated reason)
* "You've completed the goal!" (because the deck ran out)

M30 asked for Learning Mode: goals with criteria, items with schedules, sessions with a
record. The milestone was defined by what the record has to survive — that is, by the
sentences above being impossible to produce. So the acceptance criteria were:

* a goal, its items, attempts and sessions are **rows**, and the CLI and the GUI read the same
  rows in both directions;
* every grade says **who graded it** (`exact` or `self`), and there is no third answer;
* a hint is **refused** before the first attempt (exit 3 / HTTP 409) and revealed one rung at
  a time after it;
* every answer returns the new interval, ease, streak, status, due date **and the sentence
  explaining it**;
* a plan without a model says it was rules, and never invents an answer key;
* completion is an explicit act against criteria the learner wrote — never inferred.

The hard constraint inherited from M29: the GUI is a **client**. M30 adds no route that does
something the CLI cannot, and no GUI-only write path.

## 2. What was built

* **`managers/learning.py`** — the domain. `LearningGoal`, `LearningItem`, `LearningSession`,
  `Attempt` dataclasses over the v8 learning tables, five coordinator write handlers
  (`learning.goal`, `.goal_update`, `.item`, `.item_update`, `.session`, `.session_update`,
  `.attempt`, `.delete`), reads with prefix resolution (`lg_…`, `li_…`), a due query, stats,
  keyword search and a cascading delete.
* **Schema v19** — `LEARNING_V19`: `ALTER`s on the v8 tables plus `learning_sessions` and
  `learning_attempts`. Nothing was renumbered; v8's tables are still the base.
* **`application/learning.py`** — the service: `next_item`/`ask`, `hint`, `grade_answer`,
  `answer`, `schedule` (SM-2-lite), `start_session`/`review`/`end_session`, `plan` with
  `parse_plan_json` and `_rule_plan`, `report`/`write_report`, and the two refusal types
  `HintBeforeAttempt` and `NothingToStudy`.
* **CLI** — `learning` group with 22 subcommands in 12 groups (goal ×6, item ×4, plan, next,
  ask, hint, answer, session ×3, review, stats, search, report).
* **GUI** — Learning tab and view: goals list, goal detail, add-item form, next-up card with
  the `why`, a per-click hint rung, an answer form, the item table, sessions, "propose items"
  and "start a review". Eight routes under `/api/learning*`.
* **Config** — eight `learning.*` keys (§11 of `docs/LEARNING.md`).
* **`docs/LEARNING.md`**, **`tests/test_learning_m30.py`** (121 tests), and
  **`scripts/acceptance_m30.sh`** (89 checks on a fresh home, half of them through a real
  socket).

## 3. What the mode deliberately does not have

* **No model grading.** `grade_answer` compares normalised strings or asks the learner for a
  1–5 rating. A language model marking prose would be a claim the app cannot reproduce, and
  the record would have to say "a model said so".
* **No "reveal all hints".** The ladder is per level; the last rung is the answer, and
  reaching it takes three attempts at the CLI or three clicks in the page.
* **No completion inference.** A mastered deck is not a finished goal.
* **No fake curriculum.** The rules plan only reformats the learner's own words into
  checkpoints, and says so in `why`; it never produces an answer key it cannot defend.
* **No gamification.** No points, badges, streaks-of-the-day or league tables.

## 6. Bugs the milestone found (and fixed)

* **`KeyError: 'updated_at'` on the first item.** `LearningItem.to_dict()` omitted a column
  the `_apply_item` handler binds. The general lesson, now in the notes: a `to_dict()` must
  carry **every** column its `_apply_*` handler inserts.
* **The refusal pointed at a command that did not exist.** `hint` said "add some with
  `learning item edit --hint`", and `item edit` had never been written. Two consequences:
  the command now exists (`--prompt`, `--expected`, `--hint`, `--add-hint`, `--clear-hints`,
  `--explanation`, `--subtopic`, with `--clear-hints` + `--add-hint` rebuilding the ladder),
  and the same ladder cap is enforced in `update_item` as in `add_item`.
* **New material outranked due material.** The due query ordered by `COALESCE(due_at, '')`,
  which sorts `NULL` (new) first. Ordering is now `(due_at IS NULL) ASC, due_at, position`:
  review first, then new.
* **The GUI could not add an item,** so its hint button could only ever produce "this item
  has no hints" for rule-planned decks. There is now `POST /api/learning/goals/{id}/items`
  and a form in the page (a multi-line ladder is split server-side).
* **An out-of-tree flake, fixed while waiting:** `McpStdioClient._exit_message()` read
  `poll()` immediately after the stdout pipe hit EOF, which can race the child's reaping and
  report "connection closed unexpectedly" instead of "exited with status N". It now waits up
  to a second for the real status.
* **Version drift.** `pyproject.toml` and `__init__.py` are the two places the version lives;
  both moved to 0.30.0.

## 7. Deliberate limits

* Prose answers are self-rated; there is no rubric, no partial credit, no model marking.
* Media items (images, audio, generated exercises) wait for M34.
* `learning search` is keyword search over goals and items, not semantic search over a deck.
* The GUI adds items and answers them; deleting a goal or item stays a CLI act (`--yes`).
* Intervals are in days with no jitter, no per-learner model, no time-zone-aware day
  boundary beyond the stored ISO timestamps.
